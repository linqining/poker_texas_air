# poker_texas_air — Provably Fair Texas Hold'em where Cheating is Mathematically Impossible

**English** | [简体中文](README.zh-CN.md)

![License](https://img.shields.io/badge/license-BUSL--1.1-blue) ![STRK20](https://img.shields.io/badge/STRK20%20RFP-03-purple) ![Rust](https://img.shields.io/badge/rust-nightly--2026--04--15-orange)

A full-stack, provably fair online Texas Hold'em built for the
[STRK20 Private Sprint](https://strk20.starknet.io/hackathon) **RFP-03**
("Provably fair poker where cheating is mathematically impossible"):

- **Mental poker V2** — there is no trusted dealer at all. Cards are
  ElGamal-encrypted, shuffled jointly by the players, and every step
  (shuffle / remask / leave / reveal / reconstruction) carries a sigma proof.
- **Dual-proof settlement (P/G)** — the P layer (per-player secp256k1
  ownership/fold/reveal sigma proofs) is verified **on-chain** by the
  `PokerDualSettlement` Cairo contract via the Starknet EC_OP builtin; the
  G layer (canonical table-transition batches proven with Stwo
  circle-STARKs) is host-verified today with a browser-verification path, and
  is on the roadmap for on-chain verification.
- **STRK20 as chips** — players deposit STRK20 into `PokerVault`
  (1:1 chips), play, and settle through the privacy pool. A local test token
  (`PokerToken`) is provided for testnets.
- **Lean 4 formal verification** — the reconstruction protocol was
  formalized in Lean 4 with Mathlib; this process uncovered an unsoundness in
  reconstruction V2 (machine-checked counterexample) and produced the repaired
  V3 with machine-checked completeness and soundness theorems
  ([poker_protocol_lean](poker_protocol_lean)).

Beyond the RFP baseline: RFP-03 suggests a trusted dealer whose STARK proofs
make cheating detectable. This project goes further and removes the trusted
dealer entirely — dealing is jointly generated by the players and proven fair
by construction, not by trusting a host.

## Trust model & proof policy

Proof handling has three tiers, and the manifest
([strk20.json](strk20.json)) states it exactly:

| Layer | Statement | Verified where |
|---|---|---|
| **P (sigma)** | per-player ownership / fold / reveal proofs, secp256k1, keccak256 challenge | **On-chain** — `PokerDualSettlement` EC_OP builtin |
| **G (STARK)** | canonical table-transition batches (Stwo circle-STARK) | **Host** today; **browser-verifiable** via `client-wasm` proof bundles; on-chain verifier is Phase 2 |
| **Shuffle chain** | joint mental-poker shuffling with sigma proofs per step | Every client verifies proofs as they arrive |

**No independent prover service is deployed for this submission.** The
operator (host) generates G-layer proofs locally with `proving-tool`
(one full hand ≈ 29 s, proof ≈ 1.5 MB) and attests to their validity.
This is **not** a trust requirement for correctness: any player can download
the proof bundle and verify it in the browser (client-wasm), or locally with
the Rust verifier. The host is a *availability* dependency, not a
*correctness* dependency. This staged posture is explicitly allowed by
RFP-03, which asks for an on-chain STARK verifier only "eventually":

> STARK verifier (the L2 doesn't need to be on mainnet yet — the RFP
> explicitly asks for it "eventually")

Roadmap: **Phase 2** — G-STARK verifier contract on Starknet
(`cairo_verifier` direction); **Phase 3** — standalone prover service, after
which host attestation is removed entirely. Design details:
[DUAL_PROOF_PROTOCOL.md](DUAL_PROOF_PROTOCOL.md),
[DAPV_SOUNDNESS.md](DAPV_SOUNDNESS.md).

## Quick start

Prerequisites: Rust `nightly-2026-04-15` (pinned via rust-toolchain.toml),
[Scarb](https://docs.swmansion.com/scarb/) + snforge (Cairo/Starknet 2.11),
Node.js + pnpm, wasm-pack.

```bash
# 1. Rust workspace (AIR stack + protocol crates + game server)
cargo test --workspace

# 2. Cairo contracts
cd poker_contracts && scarb build && snforge test && cd ..

# 3. Browser crypto/verification WASM
wasm-pack build client-wasm --target web

# 4. Local devnet deployment of Token/Vault/Settlement
./poker_contracts/local_deploy.sh

# 5. Game server (copy texas/.env.example to texas/.env first)
cargo run -p texas

# 6. Web client
cd client && pnpm install && pnpm dev

# 7. (optional) G-layer STARK proof demo — separate toolchain, see proving-tool/README.md
cd proving-tool && ./prove-hand.sh
```

The server starts in Starknet dev mode without `STARKNET_RPC_URL` (on-chain
checks auto-pass for local play).

## Deployment

### Sepolia testnet

```bash
cd poker_contracts
export SNCAST_ACCOUNT=... SNCAST_URL=... OWNER=... PROVER=... INITIAL_SUPPLY=...
./deploy_sepolia.sh        # declares + deploys Token, Vault, Settlement, DualSettlement
```

Details and address bookkeeping: [poker_contracts/SEPOLIA.md](poker_contracts/SEPOLIA.md).
After deploying, backfill addresses and class hashes into [strk20.json](strk20.json).

### Mainnet (hackathon requirement)

At least one real STRK20 transaction on Starknet mainnet is required. The
minimal path is a deposit + withdraw through `PokerVault` (or a direct STRK20
transfer where a vault deployment is not yet justified). Record the tx hashes
in `strk20.json → transactions`.

### Configuration & secrets

All configuration is environment-driven; copy `texas/.env.example` to
`texas/.env`. Never commit private keys or deployer seeds. Deployer
credentials are read from `SNCAST_ACCOUNT` / `.env.dev` (git-ignored).

## RFP-03 alignment

Full requirement-by-requirement mapping: [docs/RFP03_ALIGNMENT.md](docs/RFP03_ALIGNMENT.md).

| RFP-03 asks for | This repo |
|---|---|
| Mental poker: no trusted dealing | `poker_protocol` ElGamal + joint shuffle + sigma proofs, Lean-verified V3 reconstruction |
| Dealer STARK obligations per street | Stwo circle-STARK stack (`src/`, `hand-bench`, `proving-tool`); Phase-1 host verification, Phase-2 on-chain |
| STRK20 as chips via a privacy pool | `PokerVault` 1:1 deposits, `PokerVaultAnonymizer` private buy-in + paymaster relay |
| Hole cards private; hand history public | Encrypted dealing; on-chain settlement commits (Poseidon) over outcomes only |
| Engine off-chain is fine | Game loop in `texas/` off-chain; settlement on-chain |

## Formal verification

[poker_protocol_lean](poker_protocol_lean) formalizes the reconstruction
protocol in Lean 4 + Mathlib. Highlights: a machine-checked counterexample
showing reconstruction V2 leaks removed slots, and the repaired V3 with
proven provenance, completeness, and soundness theorems
([SECURITY_RECONSTRUCTION.md](poker_protocol_lean/SECURITY_RECONSTRUCTION.md)).
